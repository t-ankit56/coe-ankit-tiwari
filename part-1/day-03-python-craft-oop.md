## Key learnings

### Context managers

It is a Python feature where any object with enter and exit methods sets up and cleans up resources around a block of code using the "with" statement. It is used in critical tasks such as closing a file or a database connection after work is done or in case of an error which otherwise might take up resources.

### Decorators

A decorator is used to extend or modify the behaviour of a function without changing the source code inside it. It is a function that takes a function and returns a new one wrapping it, and is applied using @decorator_name over the function.

### Generators

A Python generator is used to yield values one at a time rather than loading all into memory at once. Each yield pauses the function, and it resumes from the same spot when the next value is asked for. This is helpful when iterating over a large data set by saving memory.

### Method resolution order

The MRO is the order Python looks through a class and its parents to find a method. A child class always comes before its parents, and parents are checked in the order they are written in the class definition. In a diamond, where two parents share a grandparent, the grandparent is checked only after both parents. If Python can't build such an order it raises an error.

### Type hints

Type hints are an optional syntax introduced in Python 3.5 that helps you to explicitly state the data types of variables, function parameters and return values. It helps us in early bug detection, and makes code more readable. Python does not enforce it by default but we can use a static type checker like mypy to catch common type mismatches.

### Strategy and Observer

- In strategy pattern we use different classes which can be swapped to complete a behaviour. For example in a payment class the payment method can be swapped into card, upi etc. keeping the user facing functionality same.
- In observer pattern there are different observers that respond to events generated by a central publisher.

### SOLID

- S - Single Responsibility Principle: A class should do only one job so that it has only one reason to ever change.
- O - Open/Closed Principle: Code should be open for adding new features but closed to changing the existing, working code.
- L - Liskov Substitution Principle:  anywhere the code expects a parent type, you should be able to pass in any subtype, and the code should still work correctly without knowing which one it got.
- I - Interface Segregation Principle: A class should not be forced to depend on methods it does not use, so keep interfaces small and focused.
- D - Dependency Inversion Principle: High-level code should depend on abstractions, not on concrete low-level classes, so the details can be swapped.

### Self-explaining code

Code should be able to explain itself without the need of comments. This can be achieved by using proper naming, type hints and following principles like SOLID, DRY, and YAGNI.

### Exercise 2: Write a small context manager

`working_directory(path)` is a class-based context manager: `__enter__` saves the current directory, changes into `path` and returns it, and `__exit__` always changes back, even when the block raises. I'd use a context manager whenever something must be undone after a block, whatever happens in it: files, locks, transactions, or the working directory. The stdlib has the same thing as `contextlib.chdir`; this rebuilds it to show the protocol. Code, usage and how it works are in the [README](../code/part-1/day-03-context-manager/README.md).

| Cycle | What the test pinned | ZOMBIES | Kind |
| --- | --- | --- | --- |
| C1 | Inside the block, cwd is the target | One | Red, then green |
| C2 | After the block, cwd is restored | One | Red, green, then refactor (`target` fixture) |
| C3 | `as` gives the target path | One | Red, then green |
| C4 | An error in the block restores cwd and propagates | Exceptional | Safety net |
| C5 | A missing directory raises `FileNotFoundError`, cwd unchanged | Boundary | Safety net |

C4 and C5 passed as soon as they were written. `__exit__` runs however the block ends, and a failing `os.chdir` in `__enter__` means the block and `__exit__` never run, so neither needed new code.
